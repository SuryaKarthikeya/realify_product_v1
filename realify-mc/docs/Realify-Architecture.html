Realify turns a marketplace seller's own economics and the surrounding market into a ranked feed of decisions. The defining architectural choice is a strict separation of planes: deterministic logic decides every number and every threshold; a model layer informs with forecasts but never overrides; and a language model only phrases what the deterministic layer already decided. Numbers are never authored by an LLM. This memo documents that system end to end.

01Architectural thesis & invariants

The product is a pipeline that ingests a seller's data, runs deterministic detectors over it, and renders the results as research cards. Three planes are kept rigorously distinct, and the boundaries between them are the load-bearing invariants of the whole system.

L1 · Deterministic

Decides the numbers

Rules-as-data evaluate the seller's own economics + market facts. Every threshold, value, exposure figure and severity is computed here. Fully auditable; no ML, no LLM.

Model · Forecast

Informs, never decides

Reads metric history, returns {value, confidence, top_features}. Confidence-gated: thin data ⇒ low confidence ⇒ L1 stays authoritative. Adds forecasts & urgency.

L2 · Language

Phrases it

An LLM writes the human-facing narrative from locked numbers. It may never introduce a figure. Deterministic fallback copy if no key / offline.

Invariants (enforced, not aspirational)

  • Numbers originate in L1 only. Models and the LLM receive locked figures; they cannot mint new ones.
  • Models inform, the detector decides. A forecast can raise a card's rank or annotate it, but cannot make a card fire or change its threshold.
  • Confidentiality boundary. Customers tune thresholds; the interpretation logic (gates, priorities, phrasing pools) is Realify-managed and never serialized to the client.
  • Tenant isolation. Every row is keyed by tenant_id; every query is tenant-scoped. No cross-tenant read path exists.
  • Compliance. Amazon is never scraped. Market data comes only from Keepa and official seller APIs / public feeds.
  • Graceful degradation. Live market pulls, the LLM, and the models are each optional; the app is fully functional on deterministic own-data alone.

07Models & model architecture

The model layer sits between L1 and L2. It is contract-first and confidence-gated. Today's two models are fit-at-inference: on each run, per SKU, they read that tenant's metric_history, fit a small linear trend in pure Python, and discard it. There is no stored weight, no training job, and no cross-tenant learning yet — by design (see §12).

08Explainability — L1 · Model · L2

explain_card() assembles a three-layer provenance trace, surfaced verbatim in Explanation Mode. It is the auditable expression of the three-plane thesis.

L1

Deterministic

Inputs grouped by source (own / Keepa / news), the rule + formula, the anomaly (field op threshold), the calculation (minis) and the output finding.

Model

Forecast

If a model covers the detector: the features it read, the prediction + confidence, and the explicit note that it informs only. Otherwise: "fully deterministic (L1)".

L2

Language

The exact prompt sent to the LLM and the response returned — or a note that L2 was not invoked and deterministic copy was used.

11Tenancy, security & compliance

  • Isolation model. One tenant per deployment today; multi-tenant-ready via universal tenant_id scoping. require_tenant() gates every endpoint; there is no query path that crosses tenants.
  • Secrets. Keys (Anthropic, Keepa, news) load from a project-root .env via config.py; shell exports override. Nothing secret ships in the package (the repo carries only .env.example with blank values).
  • Confidential IP. Interpretation gates, priorities and phrasing pools live only in server code; the customer API emits booleans/counts, never the logic. Interpretation edits are admin-gated (REALIFY_ADMIN_KEY).
  • Compliance. No Amazon scraping under any path; market signal is Keepa + official APIs + public feeds (CPSC/BIS, news, trends). The collectors are the only egress and are fixture-mode by default.
  • Failure posture. Live pulls run with fail-fast timeouts + a circuit breaker; a dead source degrades to "waiting", never a hung UI. The LLM and models are independently optional.

12Constraints & the model lifecycle

Prototype honesty. Data is synthetic or uploaded; the deployment is single-machine SQLite + uvicorn; market/LLM calls aren't reachable from the build sandbox (verified only on the host). Models are fit-at-inference per tenant — there is no training job and no cross-tenant learning yet. None of this is hidden behind the demo.

The path from here to the compounding-intelligence moat is additive — the model contract does not change:

Addendum — Tenancy, Accounts & Operations (updated 2026-07-07)

This addendum records architectural changes since the original document. It is updated as part of any build that changes architecture (standing rule).

Account types (tester vs customer)

tenants.account_type ∈ {tester, customer, NULL}. Chosen at a post-signup gate, changeable until the tenant is provisioned, then locked (the lock is tied to tenants.provisioned, not to first-set). Tester = demo/ASIN + full synthesis. Customer = no synthesis: real reports only, with margin derived from price − COGS − referral. The deterministic L1 comparison (_cmp) returns False on NULL, so unprovided fields produce no card — graceful degradation is the mechanism that makes the no-synthesis path safe.

Customer ingestion & COGS

Customer onboarding establishes a SKU spine from a catalog/listings export (catalog_only_seed, all behavioural metrics NULL), validates a COGS template (reject rules: blank SKU, non-numeric/≤0, duplicate, SKU-not-in-catalog) with partial provisioning and rejects logged to pull_log, then layers other reports by kind. Floor = catalog + ≥1 valid COGS. Wipe/resynthesize are disabled for customers (server-enforced); re-upload of reports/COGS persists incrementally.

Organizations & invites

A tenant is an organization. Signup = create-org (first member, role owner). The invites table (tenant_id, email, role, hashed single-use token, status, expiry) backs a no-email invite flow: the owner generates a copy-ready body with a /join?token=… link. Tokens are stored as SHA-256 hashes; the raw token lives only in the link. users.email is globally unique → one person = one org (current limitation). Access is identical for all members for now (role recorded for a future read-only tier).

Self-service deletion

Role-aware, password-reauthenticated: single-member org or owner of a multi-member org → full delete_tenant (all tenant-scoped tables + invites + usage_events + users + the tenant row; frees the email); non-owner of a multi-member org → delete_user (leave org, org survives). Full deletes require type-to-confirm.

Operator console (/ops)

Key-only admin gate (x-realify-admin == REALIFY_ADMIN_KEY, no session). Fixed path /ops, excluded via robots.txt + X-Robots-Tag: noindex (obscurity, not a security control — the key is the control). Surfaces: system health (counts, DB size, MODE, key presence, per-source pull status), usage statistics, the tenants/orgs table, and key-gated links to this architecture doc and the engineering logbook.

API layer — routers, versioning & the identity seam (updated 2026-06-29)

The former monolithic run.py (~1050 lines, ~80 route closures inside make_app) is split into thin FastAPI routers under realify/routers/ (pages, auth, onboarding, insights, cards, settings, admin), grouped by concern, with no SQL in handlers — they call the realify.api service layer and the repositories. Two shared seams: routers/deps.py holds current() / require_tenant() / require_admin() — current() is the single identity-resolution point (session today; the Kratos + Google OIDC cutover swaps only this body, and it is transport-agnostic so a future WebSocket handshake reuses it); routers/helpers.py holds the page loader, tracking, and import logging. The partner-facing read + action surface (the insights + cards routers) is dual-mounted at both /api (existing UI, unchanged) and /api/v1 — a frozen contract for partner teams, guarded by a card-JSON contract test. A 400-line file cap (test-enforced) keeps any module from drifting back toward a monolith. Behaviour-preserving: every existing /api path is byte-identical, and tenant_id is still resolved server-side, never from the client.

Execution & serving seams — typed config, TaskRunner, ChannelConnector, model boundary (1e, 2026-06-29)

Workstream 1e formalizes the seams several partner teams depend on, all behaviour-preserving. Typed config: the scattered os.environ reads are wrapped in a frozen Settings dataclass (config.settings), with every legacy module-level name re-exported so existing call sites are untouched. TaskRunner (realify/runner.py): a small work-execution seam — submit(kind, fn, tenant_id) → job_id / get(job_id) — backed by a new tenant-scoped jobs table. An InlineTaskRunner (synchronous) and a ThreadTaskRunner (daemon thread) ship today; run_pipeline_async() is the real entry point real-time inbound events (§3H) and agent trigger-and-await (§3K) build on. The heavy implementation (external queue + workers) drops in behind this seam without touching callers. ChannelConnector (collectors/base.py): the collector contract gains a typed ConnectorConfig (mode, timeout, circuit-breaker, interval) and a reserved, unregistered AdvertisedProductCollector slot for the period-aware ads ingestion of #004 (certain-vs-estimated dollars kept separate at persistence). Model-serving boundary (models.py): every prediction is crash-isolated and stamped with a model version that flows into card provenance; a slow or failed model degrades to low confidence (silent, never wrong), so the deterministic L1 number always stands. In-process pure-Python models run in-thread; the timeout is the contract that activates when a model is served out-of-process (Team 4's build-and-deploy path). New table: jobs(id, tenant_id, kind, state, result, error, created_at, updated_at) — applied additively by run.py init.

Data layer — engine seam, Postgres, migrations & operational hardening (1c/1g, 2026-06-30)

The persistence engine moved from a single SQLite file to PostgreSQL on AWS RDS for production, behind one change-point so the application code is dialect-agnostic. Engine seam (realify/dbengine.py): url() returns the DATABASE_URL when it names a Postgres database, otherwise a sqlite:/// URL derived live from config.DB_PATH (so a test's monkeypatch is honoured); SQLAlchemy engines are cached per-URL, and SQLAlchemy/psycopg are imported lazily so a SQLite boot never loads them. Connection wrapper: a thin shim gives a psycopg connection the exact sqlite3-style API the repositories already use — ?→%s placeholder translation, and rows that support row["col"], row[0], and dict(row) — so the ~500 placeholders across 18 repositories are untouched; db.connect() branches on dialect with the SQLite path byte-identical. Upserts: the 13 INSERT OR REPLACE/IGNORE sites are rewritten to Postgres ON CONFLICT centrally in the wrapper via a _CONFLICT_KEYS map (one entry per table's real unique key; a guard test fails if a new upsert table is unmapped) — repositories are not edited. Schema: schema_to_postgres() translates the single SQLite-ism, INTEGER PRIMARY KEY AUTOINCREMENT → BIGSERIAL; everything else in the schema is already valid Postgres. Migrations: db.init_db() runs alembic upgrade head; the baseline migration is idempotent and adopts an existing SQLite database cleanly, and the two former ad-hoc PRAGMA ALTERs are now a dialect-agnostic inspector migration. Data migration (1g): realify/migrate_sqlite_to_pg.py (run.py migrate-pg [--dry-run]) copies all 33 tables by truncate-then-copy (idempotent regardless of constraints), resets serial sequences from the catalog (not a hardcoded id), and verifies row counts; it never writes to SQLite.

Production engine vs. local/test engine. SQLite is retained deliberately as the local and test engine — fast, hermetic, no network or credentials — and Postgres is production, selected purely by the presence of DATABASE_URL in the environment. The same container image runs both; the engine seam decides. RDS is a private PostgreSQL 18 instance (security group admits 5432 only from the application's security group, encrypted at rest, 7-day automated backups); the initial cutover migrated ~320k rows with every table verified source == destination. The one place dialects can still diverge (upserts, sequences, type quirks) is covered by running a throwaway local Postgres for a pre-deploy smoke when database code changes.

Operational hardening. The cutover surfaced sharp edges that are now closed: (1) dbengine.validate_url(), called by init_db(), fails with one clear line when a Postgres DATABASE_URL is malformed or has an empty password — instead of a deep driver traceback at first connect; (2) run.py doctor is a preflight that reports the dialect, validates the URL shape, opens a live connection (SELECT 1), and reports admin-key status with an exit code — the intended gate to run before a deploy and via docker exec after one; (3) the admin gate fails closed — deps.effective_admin_key() treats both an unset key and any known-weak/exposed value as unconfigured, so admin endpoints are denied until a fresh strong REALIFY_ADMIN_KEY is set, with a loud boot warning. Open items: the RDS master password is currently self-managed (folding it into Secrets Manager with boot-time injection is the remaining Phase-0 secrets task), and 1d — Postgres row-level security (DB-enforced tenant isolation, complementing the server-side tenant_id resolution) is the next data-layer feature, now unlocked by being on Postgres.

Monetization — per-seat plans, quotas & billing data model (#006, design locked)

The pricing model is per-seat: a 30-day Free trial (single user, low daily limits, hard SKU cap) → Starter at $50/seat → Growth at $199 for three users; with per-day rate limits and hard seat and SKU caps as the enforcement levers. The data model is four tables — plans, subscriptions, usage_counters, billing_events — with Stripe mirrored into billing_events. The enforcement seam, require_quota, is documented to sit beside require_tenant() in routers/deps.py, so quota checks attach at the same point identity is resolved. Status (honest): the model and the §3J partner-guide contract are locked, but the four tables and the require_quota seam are not yet built — payments is its own workstream (Team 8), and converges with the sub-second rate-limiting backplane (Redis) flagged for real-time.

Report-aware ingestion, CMAA & explainable recommendations (updated 2026-07-01)

Customer own-data is now built by a report-aware ingestion engine — realify/ingest/report_ingest.py → report_writer.py — that recognizes Amazon report kinds (Monthly Unified Transaction, COGS template, fee-preview, Sponsored Products advertised-product, Business Report, returns/storage), reconciles them (paid-only ASP, actual fees), and persists into seller_skus plus ad_performance (per-SKU per-period spend & attributed sales) and sku_revenue_period (settled revenue — the TACoS denominator), with a per-field sku_field_provenance trail (actual/reported/estimated/seller). Nothing is synthesized for a customer: an absent field stays NULL and the deterministic _cmp yields no card. Seller-owned fields are sticky — cogs, margin_floor, lifecycle_flag, and title_override are edited via POST /api/skus/edit and are not overwritten by a later re-upload (the report value is kept as a provenance alternate); title_override supplies/corrects a title when the report's is missing, resolving as title_override or title. Channel interpretation classifies each marketplace leg; unknown channels become pending_confirmations and their units are held provisional (out of judged numbers) until the seller confirms into account_interpretation. The Intelligence KPI cards re-source from these report tables when present (/api/kpis carries basis=reports for such tenants, orders for the synthetic path).

On top of this sits CMAA — Contribution Margin After Ads (realify/domain/cmaa.py, served at GET /api/cmaa): pure deterministic L1 using the locked identity break-even ACoS = gross contribution margin % (#004). Per advertised SKU it computes margin, break-even/actual ACoS, ₹ above break-even (the certain waste), and a quadrant — SCALE / FIX ADS / FIX MARGIN / CUT/DIVEST. On the three problem quadrants each row carries a recommendation object — {headline, steps[], evidence[], recoverable, guarded} — built by cmaa.recommend(): a deterministic, explainable recommended action with no LLM in the loop, where every evidence line traces to a computed figure (e.g. "Actual ACoS = ad spend ÷ ad sales = 31.3%", "Spend above break-even = spend − (ad sales × margin %) = ₹80,212"). A lifecycle-flagged SKU leads with the guard and is never told to cut — stated seller intent is respected, not overridden. This is the L1-decides / L2-phrases principle made literal: the recommendation is a number-derived artifact of the decision plane, not model output.

SQL discipline hardened with the move to Postgres-in-production: repositories must write dialect-portable SQL (no SUM(bool), no date('now', ?), no selecting non-grouped columns) since these pass the SQLite suite yet fail on Postgres; the real-Postgres smoke gates any DB-shaped change. Migrations are at head 0007 (the additive, inspector-guarded title_override column); the SKU table also freezes its header on scroll and constrains the lifecycle picker to valid values (presentation only — the field whitelist and stickiness are server-enforced).

SIMULATE — deterministic scenario projection (added 2026-07-07)

Every recommendation Realify surfaces can be projected forward — "if you take this action, here is the 30/60/90-day effect on the affected numbers, what could go wrong, and the monitoring plan" — as a deterministic scenario projection, never a prediction, badged L1 · projection · directional. The trust rule is absolute: every projected number = a current L1 value × a stated, editable assumption, emitted as a realify.domain.explain part (formula + inputs + the assumption used + result) and rendered by the client verbatim — the client never re-computes a formatted value (the "Fix-1" rule that closed an earlier NaN class, alongside the "[object Object]" render class). Assumptions carry sourced defaults, are user-editable, and re-simulate server-side; a headline confidence band (conservative/expected/optimistic) is re-derived around the current point on every run so expected == the point and the point always lies inside the band. A missing required input degrades to an honest "can't simulate" (no fabricated number); a projection resting on a weak or undefined base is marked sim_quality:"degraded" with an L1-owned reason the modal pins as a caution banner (and dims a null-base headline to "—"). The monitoring plan — 7/15/30/60-day checkpoints, each with an expected value and an explicit tripwire, where every checkpoint's ⓘ result equals the value on screen — is the trust hero.

The engine is a small module family under realify/domain/: sim_common.py (the shared spine — formatting, the linear ramp curve, the explain-cell/row builders, assumption validate+clamp, the band contract, the degrade classifier, the final-dict assembler); simulate.py (the Profit & Ads engine — one model per SCALE/FIX ADS/FIX MARGIN/CUT·DIVEST quadrant); and sim_intel.py, which dispatches by canonical detector id (interpret.detector_for) to one own-data intervention model per detector — grouped into sim_inventory.py (REORDER, DEMAND-CAPTURE), sim_flow.py (TACOS-ARREST, RETURNS-REDUCTION, CVR-LIFT, CONCENTRATION stress-test) and sim_market.py (FIX-ECONOMICS, BUY-BOX-REGAIN, PRICE-RESPONSE, REVIEW-RECOVERY, GAP-CAPTURE, plus a disclaimer-only view for a new-entrant signal that has no own-data lever). News/recall/social cards get no Simulate button — a projection there would be fabricated. Wherever a model needs a target it defaults to the tenant's own detector threshold from /api/settings/detectors (their margin floor, TACoS ceiling, days-of-cover line, CVR line, returns ceiling, Buy Box line), labelled "your line" and flagged when customized.

One endpoint serves both surfaces: POST /cmaa/simulate (dual-mounted /api + /api/v1, tenant-scoped, fail-closed) takes {sku} (Profit & Ads) or {card_id} (an Intelligence card) plus the edited assumptions, rebuilds the row server-side from L1 tenant data (build_row_card / the card's own-product SKU + latest traffic) — never a client-supplied value — and returns the Simulation. This is also the model-readiness seam: today the band comes from a deterministic formula; the same range + explain.part derivation (a formula string or a model-basis string) is exactly where a model's confidence interval will later populate, with no change to the client or the contract. Each model group is its own file to honour the 400-line-per-module cap.

Cross-channel onboarding — Shopify + guided wizard (added 2026-07-07)

Sellers can now connect a Shopify store alongside Amazon, unified at the SKU level, via two paths that converge on one pipeline. The raw path (default) is the existing drag-drop controller, extended: a header-fingerprint recognizer classifies each file, and Shopify types are just new rows. The guided wizard (optional) runs a thin interview that emits a personalized file checklist + a persisted topology, then hands back to the same controller. The spine is rules-as-DATA: realify/topology.py holds a source-aware manifest (each row is a data need with csv + inline slots live and an api slot declared-dormant for a future connected-source lane, plus shared natural_keys so a CSV upload and a later API pull idempotently converge); realify/nodegraph.py holds the wizard node graph + the answer→emit map. Adding Walmart/TikTok or an ad partner is new rows, not a new branch.

The recognizer was extracted to realify/ingest/recognizer.py (100%-signature substring match, greedy-best, with ANY-OF tokens for cases like Shopify inventory's "Available" OR "On hand"); Shopify fingerprints are sourced from the manifest so recognizer + checklist stay in lockstep. Dedup is record-level (upsert on natural_keys — overlapping re-exports never double-count; file-hash stays advisory). The onboarding data model (realify/topology_model.py) centres on Resolved<T>, the provenance primitive carrying stated/detected/effective — detection wins the number immediately on a conflict, and the user's confirmation only flips provenance STATED→RECONCILED — plus a reliability-flag lifecycle (ARMED→SATISFIED→WAIVED) whose blocks/satisfied-by mapping is data. Persistence (migration 0010, additive): tenant_topology (the resolved topology as a JSON blob) + sku_crosswalk ((channel, store_id, external_sku, external_variant_id) → canonical_sku_id = internal_sku), both registered in dbengine._CONFLICT_KEYS + TENANT_DATA_TABLES.

SKU identity resolves via ingest/crosswalk.py (auto-map when a Shopify Variant SKU equals an Amazon SKU; blank/bundle SKUs park into an unmapped bucket; a stated-IDENTICAL mismatch arms a reconcile). Financial normalization (ingest/normalize_finance.py) handles the two trust-critical cases: MCF shared inventory — an "Amazon Fulfillment" location in a Shopify inventory export is the one physical FBA pool, so it is NOT summed with Shopify stock (Shopify contributes demand; the MCF fee lives on the Amazon side, so Shopify margin stays partial until AMZ_MCF_FEES) — and booked vs settled (SHOP_ORDERS booked/reported vs SHOP_PAYOUTS settled/actual, coexisting; unmatched orders are not-yet-paid-out, a state not an error). The resolution engine + pipeline/checklist.py derive a goal-ordered checklist; pipeline/reconcile.py surfaces RC-1..RC-8 (stated-vs-detected prompts); pipeline/completeness.py yields per-goal AVAILABLE/PARTIAL/UNAVAILABLE.

Wiring: routers/wizard.py serves /api/wizard/graph + /api/wizard/resolve (answers → topology + checklist + completeness, persisted); the raw path's /api/ingest/identify now returns detection signals + reconcile prompts via ingest/rawpath.py; and /api/onboard/reports commits recognized Shopify reports through ingest/shopify_commit.py — Shopify-only SKUs become seller_skus rows (COGS/price/units/stock + provenance) while a SKU that maps to an existing Amazon SKU is linked in the crosswalk without overwriting Amazon economics (the cross-channel number merge belongs in channel_economics, a later step). The wizard UI is server-rendered in login.html, reusing the existing components + tokens (no client framework). All modules stay ≤400 lines; the Amazon flow is behavior-preserving.

Addendum 2 — Realify for Agencies (agency console, updated 2026-07-15)

What it is. A multi-tenant overlay on the same app: an agency operates N brand-accounts under a revocable envelope the brand grants; each user holds a grant within an engagement; the effective capability is intersection(envelope, grant). The whole surface is Postgres-only and feature-flagged behind AGENCY_CONSOLE (an env flag; off ⇒ every agency route returns 404). It is built, deployed, and live in production (flipped 2026‑07‑14); the seller product above is unchanged for direct customers. Code lives in realify/agency/* (domain), realify/routers/agency_*.py (routes), realify/pdp/* (policy), and realify/agency_jobs.py (periodic jobs). Migrations 0015–0030.

Tenancy, isolation & cryptography (the security spine)

  • Row-level security, enforced not advisory. 14 brand-scoped tables (engagements, envelopes, grants, brand_keys, ledger, connections, agency_ingest_rows, decisions, rollup_cache, approvals, executions, brand_pause, metering_events, invoice_lines) have ENABLE + FORCE ROW LEVEL SECURITY with policy tenant_id = ANY(current_brand_ids()). current_brand_ids() reads the transaction-local GUC app.brand_ids, set per request via set_config(..., /*local*/ true) — PgBouncer-transaction-safe.
  • No runtime role can bypass RLS. Production runs as realify_app (NOSUPERUSER, NOBYPASSRLS); even the table owner realify_admin is NOBYPASSRLS. So the actor bootstrap can't use row_security = off — instead a user reads their own grants/engagements/deep-link approval through narrow, GUC-keyed self-read policies (migrations 0027/0029, keyed to app.actor_user_id, permissive+OR'd, fail-closed). This is the deliberate, minimal exception to isolation.
  • PDP. One pure function realify.pdp.decide(envelope, grant, action) — imported everywhere, no per-route policy logic. Capability = the intersection of what the brand permitted (envelope) and what the user was assigned (grant), on the read<propose<execute ladder with per-lens autonomy ceilings.
  • Per-brand ledger + envelope crypto. Every state change appends to a per-brand hash-chained ledger; payloads are AES-256-GCM encrypted with a per-brand DEK wrapped by a master KEK (MASTER_KEK). Crypto-shred nulls the wrapped DEK → payloads become permanently unreadable while the chain still verifies. A KEK fingerprint guard (migration 0028) catches a key wrapped under the wrong KEK with a clear error instead of a cryptic AEAD failure.
  • Tenant taxonomy. tenants.tenant_kind ∈ {seller, agency_workspace, internal, sandbox} (migration 0024, replacing the overloaded is_internal). Aggregates, billable counts, and the governance drift check key off it: every active tenant must be exactly one of seller-with-Stripe · seller-under-active-engagement · agency_workspace · internal · sandbox (drift = a seller with neither Stripe nor an active engagement).

The workflow, end to end

Onboarding funnel (agency.py, agency/funnel.py, provision.py): public apply → intake (row + ops notification email) → confirmation page + applicant email → review queue → one-click approve/provision (idempotent, step-tracked, retryable) → single-use 7-day admin invite email → acceptance sets a password, session, and lands in the workspace. Consent (agency_consent.py, consent.py): the brand receives an OTP-gated, single-use, 7-day link and picks an envelope template (Full Operate / Operate ex-Pricing / Ads Only / Advise / Read-only), sets per-lens autonomy ceilings, counters, or declines; credentials are brand-owned (stub-OAuth connect). Data (ingest.py): CSV exports are auto-detected, column-mapped, and tagged source_class; an expired connection pauses, not guesses.

The action loop (the core, closed in R2–R4). The work queue (agency_console.py, queue.py) is one $-ranked stream across the actor's grant-scoped brands, each item carrying confidence, driving signal, and the brand's selling currency + the locked FX date. Acting on an item runs the maker-checker path: propose → co-sign is derived from the engagement (pricing lens or amount ≥ brand_cosign_threshold) not hardcoded; below the maker-checker threshold the proposer's Approve advances straight to approved, at/above a distinct checker is required, and a co-sign-required item emails the brand a signed deep link and waits (silence never executes, 5-day expiry). On approved, execution fires against the in-process mock marketplace (there is no real marketplace client) with the full P5 guardrails: TOCTOU re-check against the current envelope, durable idempotency key, per-account token buckets, pre-state snapshot, canary rollout with halt + rollback, and per-item Undo that restores the snapshot. Every write/rollback/halt is ledgered.

Money & evidence (R4): agency-triggered white-label reports pass a factuality gate that BLOCKS delivery of any numeric claim not emitted by the engine (a blocked report is never sent); on pass it emails the brand + ledgers. Plan & billing shows a Decisions-pool burn meter ("warn at 85%, never surprise-bill"), per-client cost allocation with a Value-delivered column, invoices + CSV export; a monthly invoice job builds from metering (Stripe stays TEST-mode). ROI v1 is the sum of executed decisions' projected impact — explicitly labeled projected, never a measured-vs-do-nothing counterfactual. The admin fleet and quality console replace raw dumps with per-agency tables (leverage vs the 1.5× gate, decisions used/pool, acceptance, MRR, needs-attention worklist, gate PASS/FAIL) and precision-by-action with below-gate coloring, dismissal reasons, acceptance drift, and ledgered mitigations.

Brand surfaces & operators. Brands get a portal (transparency log, approvals inbox, pause/narrow/revoke — "Revoking is immediate. Your data, history, and connections stay with you."), a day-0 baseline, a data-sources page, and offboarding (export + a crypto-shred deletion certificate behind a typed-confirmation + staff co-sign; the "Continue directly" option appears only when the brand ended the engagement). Locale follows the brand (₹ / en-IN for INR). The superlogin back door is hardened (admin key + @realify.ai + emailed OTP → a separate 8-hour ledgered session cookie, 3-fail lockout) and lands staff on a tester/sandbox hub; a deterministic sandbox generator + injectors seed demo worlds, and sandbox tenants are excluded from all aggregates.

Feeders, jobs & deploy

The background scheduler (agency_jobs.py, run from scheduler._loop) drives the real-brand feeders — for each active-engaged brand with ingested SKU data it (re)generates decisions, refreshes the USD-normalized rollup, and locks the daily FX rate — plus maintenance (connection-health sweep, day-90 pilot lapse, co-sign + gate expiry) and the idempotent monthly invoice build. Production is RDS Postgres behind PgBouncer (transaction pooling), the app image is baked via COPY, and requests flow Cloudflare → Caddy → uvicorn. Inbound SES bounces/complaints arrive SES → SNS → a signature-verified, flag-independent webhook → suppression list. Migrations must be applied as realify_admin before recreating the container (the runtime realify_app cannot run DDL).

Honesty markers. Execution targets an in-process mock marketplace only — no real marketplace API exists. ROI is projected, not realized. Stripe billing runs in test mode. Reports/billing/ROI ship functional with the required semantics; a few engine capabilities remain intentionally declared-not-triggered (see docs/WIRING_CENSUS.md): ledger.read_payload and ops.break_glass have no route yet, and realized-ROI reconciliation is future work.

Addendum 3 — V4 experience: parallel skin, Feature/Version Registry, Ask & Agents (updated 2026-07-23)

Parallel skin — zero-risk delivery

The V4 seller SPA is a separate file (frontend_v4.html); legacy frontend.html is never edited, so it cannot regress. pages.home() serves V4 only when the resolved skin is v4 and the file exists. All backend is additive (new routers/tables/nullable columns); the frozen /api/v1 contract is unchanged. A deploy is inert until a flag is flipped.

Feature/Version Registry (realify/flags.py)

The standing convention for shipping new work: everything ships dark behind the registry and is turned on / rolled back from the Ops page — no redeploy. Two flag kinds: version features (coexisting builds with a baseline; e.g. app_ui = legacy(baseline)/v4; pick build + scope off|internal|on) and gate features (behavior on/off, default off; ask, agents). State is DB-backed (system pseudo-tenant 0 + per-tenant in tenant_settings, no FK) and read per request → instant flip. ?skin=v4/?skin=legacy pin a session. Forward features declare requires: app_ui=v4; feature_enabled = gate AND dependency, so an "on" gate under a legacy build is inert (defined state in every combination), and behavior (e.g. agents acting) is prevented from arming until v4 is rolled. Because both skins share the same additive backend, flipping the build mid-session is non-destructive: presentation switches on next navigation, persisted V4 data (conversations, agent configs, ledger) is retained and simply hidden under legacy, and agent autonomous behavior stops (dependency unmet). Control surface: /ops Rollout card + GET/POST /api/admin/rollout.

Ask — conversational surface (realify/ask/)

Agent-shaped: a question routes through a tool layer over the tenant's real data (same domain code as the cards), a narrator composes structured response parts, and the turn streams as SSE and persists. narrator.py is the single model swap point — today a data-grounded stub; a self-hosted model implements the same compose() contract, dispatched on the model's provider. Tenant-scoped, monthly usage cap. Tables ask_* (migration 0039).

Agents — the workforce (realify/agents/)

A hire→configure→assign→monitor framework: specialist catalog, an autonomy ladder (Observe→Suggest→Assist→Act, start Observe), server-side guardrails, a hash-chained Autonomy Ledger (tamper-evident, reversible), and the pricing scope hierarchy (Category plane → Subcategory CPS → Item state; policy inherits down, outcomes aggregate up). The flagship Pricing agent "runs like a GMM" (four clocks / five signals / ITL-ARB-01) and consumes the RIA models for the math. Behavior is gated (feature_enabled('agents'), default off) and Act is held until the RIA models + real Amazon write-back land; testers get seeded sample decisions. Tables agent, agent_task, agent_decision, pricing_* (migration 0041). See AGENTS-ARCHITECTURE.md.
